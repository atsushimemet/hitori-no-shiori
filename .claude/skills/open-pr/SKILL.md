# open-pr — 開発完了後の commit → push → 日本語PR 作成

ローカルでの実装が完了したあと、この手順で **コミット・プッシュ・PR作成** までを
まとめて行う。この作業は外向き（GitHubへのpush / PR公開）なので、**最後のPR作成前に
ユーザーへタイトルと本文案を提示して承認を得てから** `gh pr create` を実行する。

Codex でこのスキルを読む場合も、ユーザーが `open-pr` / `open pr` を明示したら
汎用の GitHub PR 作成手順より本スキルを優先する。`gh pr create` ではなく GitHub
connector など別の手段で PR を作成する場合でも、下記の PR 本文フォーマット
（箇条書きちょうど5つ + `close #<番号>`）は必ず維持する。

## 前提の確認

1. カレントディレクトリが git リポジトリで、`main` 以外のフィーチャーブランチに
   いることを確認する（`git branch --show-current`）。`main` にいる場合は先に
   ブランチを切る（ブランチ名の慣例は `hitori-no-shiori-issue-<番号>`）。
2. 関連 Issue 番号を特定する。ブランチ名 `hitori-no-shiori-issue-<番号>` から
   `<番号>` を抽出する。抽出できない場合はユーザーに確認する。この番号は後段の
   `close #<番号>` に使うため **必ず確定させる**。
3. `git status` と `git diff` で、これからコミットする変更内容を把握する。
   意図しないファイル（`.env` など）が含まれていないか確認する。

## 検証（コミット前に必ず実施）

PR本文の5つ目の箇条書きは「検証結果」を書くのが本リポジトリの慣例。先に流しておく。

```bash
npm run lint
npm run build
```

- 失敗したら **コミットせず**、内容をユーザーに報告して指示を仰ぐ。
- 変更内容によっては該当する方だけで十分な場合もある。判断に迷えば両方流す。

## 1. コミット

- 変更を `git add` する（対象を絞る。`git add -A` は不要ファイルを巻き込むので注意）。
- コミットメッセージは **日本語の簡潔な要約1行**（本リポジトリの慣例）。
  例: `予定完了後のトップ導線を追加`、`iOS Chromeでチャット入力時の自動拡大を抑止`
- 命令形の体言止め／過去形どちらも可だが、直近のコミット履歴に文体を合わせる
  （`git log --oneline -10` で確認）。

```bash
git commit -m "<日本語の要約>"
```

## 2. プッシュ

現在のブランチをリモートへプッシュする。初回は upstream を設定する。

```bash
git push -u origin HEAD
```

## 3. PR タイトルと本文を作成

**タイトル**（日本語・簡潔）:
- 変更の主旨が一目で分かる短い日本語にする。
- 例: `予定完了後のトップ導線を追加` / `iOS Chromeでチャット入力時の自動拡大を抑止`

**本文**（日本語・箇条書きちょうど5つ ＋ Issueクローズ行）— このリポジトリの必須フォーマット:
1. 何を追加/変更したかの中心的な内容
2. 具体的な実装・UIの詳細（1）
3. 具体的な実装・UIの詳細（2）
4. 既存への影響範囲やユーザー体験上の配慮
5. 検証結果（例: `npm run lint` と `npm run build` で検証済みです。）

- 各行は `- ` で始める。文末は「〜しました。」「〜です。」調で揃える。
- コード名・パス・コマンドは `` ` `` で囲む（既存PRの書き方に合わせる）。
- 冒頭や末尾に見出し・絵文字・定型フッターは付けない（既存PRに倣いプレーンに保つ）。

### Issue 自動クローズ（必須）

- 箇条書き5つに続けて、空行を1つ挟み、**必ず `close #<番号>` を1行加える**。
- この一行があることで、**PR がマージされると同時に対応 Issue も自動でクローズ** される。
- `<番号>` は「前提の確認」で確定させた Issue 番号を使う。
- キーワードは小文字の `close` で統一する（`close #<番号>`）。
- 対応する Issue が存在しない変更の場合のみ、この行を省略してよい。

### 参考：既存PRの本文フォーマット例（末尾に `close #<番号>` を付与）

```
- 共通レイアウトにヘッダーを追加しました。
- ヘッダーに「ひとりの栞」のテキストリンクを配置しました。
- `next/link` を使い、どの画面からもトップページ `/` へ遷移できるようにしました。
- 既存のページ構成や各画面のコンテンツには影響しない範囲で実装しました。
- `npm run lint` で静的検証を通過しています。

close #35
```

## 4. ユーザー承認 → PR 作成

1. 生成したタイトル・5つの箇条書き本文・`close #<番号>` 行を **ユーザーに提示** し、
   承認を求める。
2. 承認後、ヒアドキュメントで本文を渡して PR を作成する。GitHub connector など
   `gh pr create` 以外の方法で作成する場合も、`body` には同じ本文をそのまま渡す。

```bash
gh pr create --base main --title "<日本語タイトル>" --body "$(cat <<'EOF'
- <箇条書き1>
- <箇条書き2>
- <箇条書き3>
- <箇条書き4>
- <箇条書き5>

close #<番号>
EOF
)"
```

3. 作成された PR の URL をユーザーに報告する。マージ時に Issue #<番号> が
   自動クローズされる旨も伝える。

## 注意

- 検証（lint/build）が通らないまま push / PR しない。
- `.env` など秘匿ファイルをコミットに含めない（`.gitignore` を確認）。
- 箇条書きは **必ず5つ**。多すぎ・少なすぎは本リポジトリの慣例から外れる。
- `close #<番号>` を **付け忘れない**。これが無いとマージしても Issue が閉じない。
